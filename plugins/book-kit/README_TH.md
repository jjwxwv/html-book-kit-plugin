# Claude HTML Book Kit v11.5 — Plugin Edition (คู่มือภาษาไทย)

Plugin สำหรับ Claude Code ที่แปลงเอกสารประกอบการเรียน (PDF / PPTX / DOCX / Markdown) ใน `sources/` เป็น **หนังสือสรุปบทเรียนแบบ HTML** ที่ครบถ้วน ถูกต้อง อ่านแล้วเห็นภาพ อัปเดตได้ และประหยัด token

หลักการ: *อ่านต้นฉบับให้ครบ เข้าใจให้หมด แล้วค่อยสรุป ทุกการตัดและการรวมต้องตรวจสอบย้อนกลับได้* และ *สิ่งที่ตรวจด้วย script ได้ ต้องตรวจด้วย script ไม่ฝากไว้กับ prompt*

## มีอะไรใหม่ใน v11.5 (แก้ตามผลตรวจ v11.4)

ผลตรวจ v11.4 พบว่า requirement ทั้ง 9 ข้อผ่าน และไม่มีปัญหาระดับสูง สิ่งที่พบคือ 7 จุดที่งานหลุดการติดตามเมื่อรันสะดุด หรือที่ยังพึ่งการอ่านของ auditor ทั้งที่ script ตรวจได้ รุ่นนี้แก้ทั้งหมด

1. **unit ที่ถูกแก้ตรงตำแหน่งเดิมค้างในบันทึกจนกว่า architect จะยืนยัน (F1)** เมื่อต้นฉบับถูกแก้ตรงจุดเดิม unit ใหม่จะรับตำแหน่งของ unit เก่าใน plan โดย script เดิมรายการนี้ถูกบอก architect ครั้งเดียว ถ้ารันสะดุดตรงนั้นก็ไม่มีใครบอกอีก ตอนนี้รายการค้างอยู่ใน `plan/reextracted.json`: scan แจ้งเป็น `replan` ขั้น `--plan` แจ้งซ้ำพร้อมคำเตือน `plan.replaced_unreviewed` และ validator ส่งต่อให้ auditor รายการปิดเมื่อ architect เขียน `"reextracted_reviewed"` ลงใน plan (script ลบ key นี้ออกเอง) หรือเมื่อ architect ย้าย unit นั้นไปหัวข้ออื่น ส่วน extraction ที่ถูกแก้ตาม audit โดยต้นฉบับไม่เปลี่ยน ไม่ต้องยืนยัน
2. **`content.level` ที่ผิดหยุดตั้งแต่ขั้น plan (F2)** เดิม `sync_state.py --plan` ทำงานต่อที่ระดับ 2 เงียบ ๆ แล้วไปถูกบล็อกหลังเขียนเสร็จ ตอนนี้บล็อกด้วย `config.level` ก่อนจะแจ้งบทใดให้ writer
3. **ช่วงที่ต้องอ่านใหม่แจ้งเป็นช่วง (F3)** `read_ranges` เป็น `l.13-17` แทนที่จะแจกทีละบรรทัด และไม่ล้ำเข้าไปใน unit ที่พิสูจน์แล้วว่าไม่ถูกแตะ
4. **ไม่มีป้ายเวอร์ชันที่ค้างได้ (F4)** หัวไฟล์ของ script, template และ skill ไม่ระบุเวอร์ชันของตัวเองแล้ว เวอร์ชันอยู่ที่เดียวคือ `plugin.json` กับ `KIT_VERSION` และมี test ตรวจ
5. **extraction ที่อ่านไม่จบถูกส่งกลับไปอ่านต่อ (F5)** เดิมถ้า stamp รายงาน `extraction.truncated` แล้วรันหยุด รอบถัดไปจะวางแผนและเขียนบทจาก extraction ที่ไม่ครบ แล้วค่อยถูกบล็อกตอน validate ตอนนี้ scan แจ้งไฟล์นั้นใน `extract` ด้วยเหตุผล `truncated` พร้อม `resume_after` analyst อ่านต่อจากจุดนั้นโดยไม่อ่านส่วนแรกซ้ำ
6. **draft มีได้แต่เนื้อหา (F6)** `<script>`, `<style>`, `<nav>`, `<iframe>`, attribute แบบ `onclick=` และลิงก์ `javascript:` ใน draft ทำให้ validate ไม่ผ่าน (`draft.foreign_markup`) สีที่เขียนตายตัว เช่น `fill="#000"` หรือ `style="color:red"` ถูกเตือน (`draft.hard_colour`) ส่งให้ writer แก้หนึ่งรอบ ที่เหลือ auditor ตัดสิน เพราะสีแบบนี้ไม่เปลี่ยนตามธีม รูปที่วาดด้วยสีดำจะมองไม่เห็นใน dark mode
7. **`--rewrite` ค้างจนกว่าจะเขียนจริง (F7)** คำขอเขียนใหม่ทั้งเล่มถูกบันทึกไว้กับแต่ละบท บทที่ยังไม่ถูกเขียนใหม่ทำให้ validate ไม่ผ่าน (`draft.stale`) และถูกแจ้งซ้ำในรอบถัดไปแม้ไม่ใส่ `--rewrite`

จุดเล็กอีก 2 จุด: ประเด็นที่ script ตั้งเองตอนรวมผล audit (บทที่ไม่ได้ตรวจ, draft ที่ถูกแก้ระหว่าง audit) ไม่ซ้ำสองรายการในรายงานถัดไป และปิดเองเมื่อไม่จริงแล้ว และเนื้อหาเสริมที่ติด `data-supplement` ซ้ำสองที่ถูกเตือน

## ที่มาจาก v11.4 (แก้ตามผลตรวจ v11.3)

ผลตรวจ v11.3 พบว่า requirement ทั้ง 9 ข้อผ่านบนเส้นทางปกติ แต่มีบั๊ก 1 จุดที่ v11.3 สร้างขึ้นเอง และช่องโหว่ 2 จุดที่ยังฝากไว้กับ prompt รุ่นนี้แก้ทั้งหมด

1. **แก้ `.pptx` / `.docx` แล้ว analyst ได้ไฟล์ที่ต้องเปิดเสมอ (H1)** ใน v11.3 รายการของไฟล์ Office ที่ถูกแก้ใช้ key `read` สองความหมาย (path ของไฟล์ที่ต้องเปิด และรายการช่วงที่ต้องอ่าน) ค่าหลังเขียนทับค่าแรก analyst จึงไม่รู้ว่าต้องเปิดไฟล์ไหน ตอนนี้แยกเป็นสอง key: `read` คือไฟล์ที่เปิด `read_ranges` คือช่วงสไลด์หรือบรรทัดที่ต้องอ่าน และสำเนา pre-extract ของเวอร์ชันเก่าถูกลบเมื่อเวอร์ชันใหม่ถูก stamp (ต้นฉบับหนึ่งไฟล์มีสำเนาเดียว)
2. **เลข unit ใน plan เลื่อนตามด้วย script ไม่ใช่ architect (M1)** เมื่อต้นฉบับถูกอ่านใหม่ เลข unit เปลี่ยน v11.3 แค่ *บอก* architect ว่า unit ไหนย้ายไปเลขไหน แล้วให้ architect แก้ plan เอง ถ้าแก้พลาดไม่มี script ใดจับได้ และถ้ารันสะดุดระหว่างทาง แผนที่การย้ายหายไปเลย ตอนนี้ `sync_state.py --stamp` แก้เลขใน plan เอง: unit ที่แค่ย้ายเลข และ unit ที่ถูกแก้เนื้อหาตรงตำแหน่งเดิม (นับเป็น "แทนที่") ยังอยู่หัวข้อเดิม สิ่งที่เหลือให้ architect ตัดสินคือ unit ที่เพิ่มมาใหม่ และหัวข้อที่ unit หายหมด ซึ่งจะค้างเป็น `coverage.gap` / `plan.section_emptied` จนกว่า plan จะตอบ จึงรันต่อจากที่ค้างได้โดยไม่ผ่านไปเงียบ ๆ
3. **การอนุมัติแก้ตาม audit คือการพิมพ์คำสั่ง และ script ตรวจจริง (M2)** เดิม "1 อนุมัติ = 1 รอบ" เป็นกติกาใน prompt อย่างเดียว ตอนนี้มี 3 ชั้น: (ก) `apply-fixes` เป็นคำสั่งที่ Claude เรียกเองไม่ได้ ต้องพิมพ์ `/book-kit:apply-fixes` เท่านั้น (ข) plugin มี hook ที่บันทึกทุกครั้งที่คุณพิมพ์คำสั่งนั้น และ `sync_state.py --set-audit approved` ต้องใช้บันทึกนี้ 1 ครั้งต่อ 1 รอบแก้ ถ้าไม่มีจะปฏิเสธด้วย `audit.gate` (ค) รายงานหนึ่งฉบับแก้ได้ไม่เกิน `audit.max_fix_batches` รอบ (ค่าเริ่มต้น 5) การตอบ "ใช่" เป็นข้อความธรรมดาจึงไม่เริ่มการแก้อีกต่อไป Claude จะบอกให้พิมพ์คำสั่ง
4. **บรรทัดหัวไฟล์ของ kit ไม่นับเป็นเนื้อหา (L1)** บรรทัดแรกของสำเนา pre-extract มี SHA ของต้นฉบับ จึงเปลี่ยนทุกครั้งที่ไฟล์ถูกแก้ เดิมบรรทัดนี้ถูกส่งให้ analyst อ่าน และทำให้ unit แรกไม่ถูกพิสูจน์ว่า "ไม่ถูกแตะ" ได้เลย
5. **`--rewrite` ตัดสินด้วย script (L2)** `sync_state.py --plan --rewrite` แจ้งทุกบทเป็นโหมดเขียนทั้งบท คำสั่ง build ไม่ต้องอ้างรายการที่ script ไม่ได้พิมพ์
6. **ระบุเวอร์ชัน Claude Code (L3)** ดูหัวข้อ "ติดตั้ง"

## ที่มาจาก v11.3 (แก้ตามผลตรวจ v11.2)

ผลตรวจ v11.2 พบ 8 จุด (G1–G8) ที่ระบบรายงานว่าเรียบร้อยทั้งที่ยังไม่เรียบร้อย หรือใช้ token มากกว่าที่ควร รุ่นนี้แก้ทั้งหมด

1. **ประเด็น audit แยกตามระดับการสรุป (G1)** รายงาน audit หนึ่งฉบับตรวจหนังสือ "ฉบับ" เดียว (draft ของระดับเดียว) แต่ละระดับจึงมีสายรายงานของตัวเอง การ audit ฉบับระดับ 1 ไม่ปิดและไม่ยกประเด็นของฉบับระดับ 2 ไปปนอีกแล้ว เมื่อสลับระดับ ระบบแจ้งว่าอีกฉบับยังมีประเด็นค้างกี่ข้อ
2. **ประเด็นที่ยังไม่ได้ตอบไม่หายเมื่อ audit ซ้ำ (G8)** auditor รอบใหม่ได้รับประเด็นค้างของบทที่ตนตรวจ และต้องลงความเห็นทีละข้อ ประเด็นจะปิดก็ต่อเมื่อ auditor ระบุว่าแก้แล้วเท่านั้น ถ้าไม่พูดถึง ระบบยกไปรายงานใหม่พร้อมป้ายว่า "ยังไม่ได้ตรวจซ้ำ"
3. **apply-fixes ที่ค้างกลางทางสั่งต่อได้ (G6)** รายงานที่ค้างสถานะ `approved` ถูกบอกใน scan และ `/book-kit:apply-fixes` ทำต่อจากประเด็นที่ยังเปิดอยู่
4. **แก้ต้นฉบับนิดเดียว เขียนใหม่นิดเดียวจริง (G3)** (ก) ลายนิ้วมือของหัวข้อไม่รวมเลข unit และตำแหน่งในไฟล์อีกต่อไป unit ที่แค่เลื่อนตำแหน่งจึงไม่ทำให้หัวข้อถูกเขียนใหม่ (ข) สำหรับไฟล์ข้อความ `.docx` และ `.pptx` ระบบเก็บ hash ของช่วงบรรทัดหรือสไลด์ที่แต่ละ unit อ่านมา เมื่อไฟล์เปลี่ยน script พิสูจน์ได้เองว่า unit ไหนไม่ถูกแตะ analyst คัดลอก unit เหล่านั้นและอ่านเฉพาะช่วงที่เปลี่ยน (ค) หลังอ่านใหม่ script บอก architect ว่า unit ไหนแค่ย้ายเลข ไหนใหม่ ไหนหายไป
5. **การตั้งค่าที่ writer ใช้ถูกตรวจด้วย script (G4)** เปลี่ยน `book.language` แล้วบทที่เขียนด้วยภาษาเดิมถูกจัดให้เขียนใหม่ ปิด KaTeX หรือ Mermaid ทั้งที่ draft ยังมีสูตร TeX หรือแผนภาพ Mermaid จะ block (`draft.raw_tex`, `draft.mermaid_off`) และส่งให้ writer แปลง ปิดคำถามทบทวนแล้ว build ซ่อนให้โดยไม่ใช้ token เปิดกลับแล้วบทที่ยังไม่มีถูกส่งให้ writer เติม ส่วนการเปลี่ยน `audience` / `style_notes` ไม่เขียนอะไรใหม่ ระบบแจ้งว่าบทใดยังใช้สำนวนเดิม
6. **ท้ายไฟล์ข้อความที่ไม่ได้อ่านถูกจับ (G2)** มีเนื้อหาตั้งแต่ 8 บรรทัดขึ้นไปหลังบรรทัดสุดท้ายที่ unit อ้างถึงจะ block ถ้ามี 3–7 บรรทัดจะเตือนให้ auditor ตรวจ
7. **ไฟล์ต้นฉบับชื่อซ้ำในบทเดียวกันไม่ชนกัน (G5)** เช่น `ch5/lecture/slides.pdf` กับ `ch5/tutorial/slides.pdf` หรือ `5.1 notes.md` กับ `5.1 notes.txt` ได้ที่เก็บ extraction คนละไฟล์
8. **การซ่อมไม่เขียนทั้งบท (G7)** เมื่อบทถูก build แล้ว slice ของบทนั้นไม่มีคำสั่ง "เขียนทั้งบท" ค้างอยู่ การซ่อมจาก validator และการแก้ตาม audit จึงเป็นการแก้เฉพาะจุดเสมอ

## ที่มาจาก v11.2 (แก้ตามผลตรวจ v11.1)

ผลตรวจ v11.1 พบว่ามี 5 ทางที่เนื้อหาตกหล่นหรือค้างเก่าได้โดย validator ยังรายงานผ่าน รุ่นนี้ปิดทั้งหมดด้วย script

1. **หัวข้อที่มีแต่ชื่อไม่ผ่านอีกต่อไป** บัญชี coverage พิสูจน์ได้แค่ว่า plan นับ unit ครบ ไม่ได้พิสูจน์ว่า unit อยู่ในบทจริง ตอนนี้หัวข้อที่ครอบคลุม unit แต่ไม่มีเนื้อหาใต้หัวข้อจะ block (`draft.section_empty`) และหัวข้อที่เนื้อหาน้อยผิดปกติเมื่อเทียบกับจำนวน unit ถูกส่งให้ auditor (`content.section_thin`)
2. **ตรวจว่าอ่านถึงท้ายไฟล์ได้ทุกชนิด** DOCX, Markdown, text และ HTML ตรวจด้วยเลขบรรทัด PDF นับหน้าได้เองโดยไม่ต้องติดตั้ง `pypdf` และเมื่อนับไม่ได้จริง ๆ ระบบรายงานว่า "ยังไม่ได้ตรวจ" (`extraction.length_unverified`) แทนการปล่อยผ่าน
3. **draft ผูกกับสิ่งที่ writer ได้รับตอนถูกสั่งงาน** ไม่ใช่สิ่งที่มีอยู่ตอน build งานที่ค้างกลางทางแล้วต้นฉบับถูกแก้จึงถูกจับได้
4. **รูปที่อ่านไม่ได้ถูกแจ้งให้เห็น** ไฟล์ `.pptx`/`.docx` ที่มีรูปหรือ object ฝังถูกแจ้งชื่อทั้งตอน scan และในรายงานของ auditor พร้อมวิธีแก้ (export เป็น PDF) และ architect ถูกห้ามใช้เนื้อหาเสริมมาแทนรูปที่มองไม่เห็น
5. **ประเด็น audit ไม่หลุด** ประเด็นที่ยังเปิดอยู่ถูกยกไปอยู่ในรายงานฉบับใหม่เสมอ สถานะรายงานเปลี่ยนด้วย script เท่านั้น และ auditor ไม่แก้ไฟล์รายงานเองอีก
6. **ไฟล์ Office และบรรทัดยาว** อ่าน endnote ได้ รายการแบบมีเลขยังเป็นรายการแบบมีเลข และบรรทัดที่ยาวเกิน 1,800 ตัวอักษรถูกตัดบรรทัดใหม่ก่อนให้ analyst อ่าน (รวมถึงไฟล์ Markdown/text/HTML ที่มีบรรทัดยาว)

## ที่มาจาก v11.1 (แก้ตามผลตรวจ v11.0)

1. **ห่วงโซ่หลักฐานจากต้นฉบับถึงหน้าหนังสือเป็นเชิงกลทั้งเส้น** ต้นฉบับเปลี่ยนแต่ยังไม่อ่านใหม่ หรืออ่านใหม่แล้วแต่ยังไม่เขียนบทใหม่ ระบบจับได้เองและบอกหัวข้อที่ต้องเขียนใหม่
2. **ไฟล์ Office ไม่ทำเนื้อหาหายเงียบ** สมการ กล่องข้อความที่มีสมการ SmartArt ข้อมูลกราฟ และ footnote ถูกอ่านครบ และไม่ต้องติดตั้ง python-pptx / python-docx อีก
3. **เก็บ draft แยกตามระดับการสรุป** มีได้ทั้งสองฉบับในโปรเจกต์เดียว สลับกลับไประดับที่เคยเขียนแล้วไม่เสีย token
4. **บัญชี coverage สร้างจาก plan** ไม่มีสองไฟล์ที่ขัดกันได้ และนับ unit จากเนื้อ extraction จริง
5. **แทรกบทกลางเล่มได้** เปลี่ยนเลขโฟลเดอร์ต้นฉบับ แล้วระบบเลื่อนเลขทั้งเล่มให้โดยไม่เขียนเนื้อหาใหม่
6. **audit แยกรายบทและสุ่มตรวจ extraction เทียบต้นฉบับ** รวมรายงานด้วย script
7. **ทำต่อจากที่ค้างได้** งานที่เสร็จแล้วไม่ถูกทำซ้ำ ทั้งการอ่านต้นฉบับและการเขียนบท

## เริ่มใช้งาน

1. สร้างโฟลเดอร์หนังสือ เปิด terminal ในโฟลเดอร์นั้น รัน `claude` แล้วพิมพ์ `/book-kit:init "ชื่อหนังสือ"`
2. วางไฟล์ต้นฉบับใน `sources/` ตามรูปแบบใน `sources/README.md` (เลขนำหน้าคือโครงสร้างบท)
3. เปิด `book.config.json` ตรวจชื่อหนังสือ และเลือก `content.level` (1 หรือ 2)
4. พิมพ์ `/book-kit:build-book` เสร็จแล้วเปิด `book/index.html`
5. ถ้า audit พบประเด็น ระบบจะ **รายงาน → ถาม → หยุด** ถ้าต้องการให้แก้ ให้พิมพ์ `/book-kit:apply-fixes` (การพิมพ์คำสั่งนี้คือการอนุมัติ 1 รอบแก้ การตอบ "ใช่" เฉย ๆ ไม่เริ่มการแก้)

> ครั้งแรกหลัง `init` กติกา permission จะมีผลเมื่อเริ่ม session ใหม่ ถ้า Claude Code ถามสิทธิ์ระหว่าง build ครั้งแรก กดอนุญาตได้ตามปกติ
> ถ้า build ถูกขัดจังหวะ สั่งคำสั่งเดิมซ้ำได้เลย ระบบทำต่อจากที่ค้าง

## ระดับการสรุป (`content.level`)

หลักข้อเดียวที่ทั้งระบบยึด: **ระดับเปลี่ยนความหนาแน่นของคำอธิบาย ไม่เปลี่ยนความครอบคลุม** ทั้งสองระดับใช้ plan และรายการเนื้อหาเสริมชุดเดียวกัน นิยาม สูตรพร้อมความหมายของสัญลักษณ์ เงื่อนไข ข้อยกเว้น ลำดับขั้นตอน และตัวเลขสำคัญต้องอยู่ครบทุกระดับ

| | ระดับ 1 ทบทวนก่อนสอบ | ระดับ 2 เรียบเรียงใหม่ (ค่าเริ่มต้น) |
|---|---|---|
| ผู้อ่าน | เรียนมาแล้ว ต้องการทวนให้ครบและเร็ว | กำลังเรียน ต้องเข้าใจได้จากเล่มนี้ |
| รูปแบบ | ตาราง รายการคำศัพท์ กล่องสูตร ขั้นตอนเป็นข้อ ร้อยแก้วเท่าที่จำเป็น | ร้อยแก้วอธิบาย จัดลำดับใหม่เพื่อการสอน ไม่ซ้ำซ้อน |
| ตัวอย่าง | ย่อเหลือแบบแผน 1–2 บรรทัดต่อกรณี | ตัวอย่างทำให้ดูหนึ่งตัวอย่าง เพิ่มเมื่อเป็นกรณีต่าง |
| การพิสูจน์/ที่มา | ผลลัพธ์ เงื่อนไข และแนวคิดหลัก ยกเว้นเนื้อหาที่ "ขั้นตอนคือสิ่งที่สอน" จะคงทุกขั้น | ทีละขั้นตามที่ต้นฉบับสอน |
| ท้ายบท | สรุป และคำถามทบทวนที่ลิงก์กลับไปหัวข้อ | สรุป |

**"ครบ" ในระดับ 1 ตรวจอย่างไร:** นอกจาก auditor แล้ว validator มีหลักฐานเชิงกล 3 อย่าง (เป็นคำเตือนให้ auditor ตัดสิน) คือ ทุกกล่องสูตรต้องมีบรรทัดบอกความหมายสัญลักษณ์ คำสำคัญที่ analyst บันทึกไว้ของแต่ละ unit ต้องปรากฏในบท และ unit ที่เป็นขั้นตอนต้องมีรายการขั้นตอนเป็นข้อ

**สลับระดับ:** แก้ `content.level` แล้วสั่ง `/book-kit:update-book` ครั้งแรกของแต่ละระดับระบบเขียน draft ทุกบทที่ระดับนั้น (ไม่อ่านต้นฉบับซ้ำ ไม่วางแผนใหม่) หลังจากนั้น draft ของทั้งสองระดับถูกเก็บไว้คู่กัน **สลับกลับไปมาไม่เสีย token** และเมื่อต้นฉบับเปลี่ยน ระบบเขียนใหม่เฉพาะหัวข้อที่กระทบของระดับที่กำลังใช้

**อยากเปิดอ่านสองฉบับพร้อมกัน:** `book/` เก็บฉบับของระดับที่ตั้งอยู่ ให้คัดลอกโฟลเดอร์ `book/` ไปเก็บไว้ที่อื่น (เป็นไฟล์ static เปิดได้เลย) แล้วสลับระดับเพื่อ build อีกฉบับ

**คำถามทบทวน (ระดับ 1):** เป็นคำถามล้วน ไม่เพิ่มข้อเท็จจริง แต่ละข้อลิงก์ไปหัวข้อที่ตอบได้ ปิดได้ด้วย `"recall_questions": false`

## หน้าตาและชุดสี

- **หนึ่งบทหนึ่งสี:** เลขบทในสารบัญ แถบหัวบท แถบไฮไลท์คำสำคัญ และแถบความคืบหน้าใช้สีเดียวกัน กล่องแต่ละชนิด (นิยาม สูตร ตัวอย่าง หมายเหตุ ข้อควรระวัง สรุป คำถามทบทวน) มีสีและป้ายกำกับของตัวเอง
- **ผู้อ่านปรับเองได้:** ปุ่ม "Aa" มุมขวาบนเลือกชุดสี ขนาดตัวอักษร และล้างสถานะการอ่าน ปุ่มข้างกันสลับธีมสว่าง มืด หรือตามระบบ ค่าที่เลือกเก็บใน browser ของผู้อ่าน
- **ชุดสีสำเร็จรูป:** `notebook` (สมุดจด), `vivid` (สดใส), `ocean` (ทะเล), `sunset` (อาทิตย์ตก) ตั้งค่าเริ่มต้นของเล่มด้วย `ui.palette` หรือสั่ง `/book-kit:design ocean`
- **ชุดสีกำหนดเอง:** ใส่ `ui.custom_palette` แล้วตั้ง `"palette": "custom"` หรือสั่ง `/book-kit:design` พร้อมบอกสิ่งที่ต้องการ เช่น "อยากได้โทนเขียวเป็นหลัก"

```json
"ui": {
  "palette": "custom",
  "custom_palette": { "label": "ชุดสีของฉัน", "base": "notebook", "paper": "warm", "chroma": 1.1,
                      "hues": { "primary": "#0f766e", "summary": 95 } }
}
```

สีทุกชุดสร้างจากสูตรที่คำนวณความสว่างให้คู่ตัวอักษรกับพื้นหลังผ่าน WCAG AA ทั้งธีมสว่างและมืด คุณกำหนดได้เฉพาะเฉดสี ความสด และโทนกระดาษ ส่วนความสว่างระบบคำนวณเอง

## Pipeline ภายใน

แต่ละขั้นของ agent มี script คั่นตรวจก่อนไปขั้นถัดไป ถ้าไม่ผ่านจะหยุดก่อนเสีย token ในขั้นที่แพงกว่า

```text
scan_sources.py --status      บอกว่าต้องอ่านไฟล์ไหน (ตัดสินจาก SHA-256 ของ extraction) ต้องเขียนบทไหน
   ↓                          และมีไฟล์ที่ไม่รองรับหรือไม่
extract_office.py --all       แปลง .pptx/.docx เป็น markdown และตัดบรรทัดที่ยาวเกินของไฟล์ข้อความ (script)
sync_state.py --sources       ปรับ state ตามไฟล์ที่ย้าย ลบ หรือเปลี่ยนเลขบท (script)
   ↓
book-kit:source-analyst       อ่านต้นฉบับ 1 ไฟล์ต่อ 1 agent ครั้งเดียวต่อเวอร์ชัน → extraction
sync_state.py --stamp         ประทับ SHA และจำนวน unit ตรวจเลข unit และตรวจว่าอ่านถึงหน้า/สไลด์/บรรทัดสุดท้าย
                              ถ้าเป็นไฟล์ที่อ่านใหม่ เลื่อนเลข unit ใน plan ตามให้เอง และบันทึกสิ่งที่ architect ต้องตอบ
   ↓
book-kit:book-architect       วางโครงบท ลำดับ รวมซ้ำ ระบุว่าแต่ละ unit ไปอยู่ไหน และเนื้อหาเสริม
sync_state.py --plan          ตรวจ plan สร้าง coverage.json และ slice รายบท บอกว่าต้องเขียนบทไหนแบบใด
                              และบันทึกว่า writer แต่ละตัวได้รับ input ชุดใด
   ↓
book-kit:chapter-writer       เขียนเนื้อหารายบทจาก slice ของตัวเอง ตามระดับที่ตั้ง
build_book.py                 ประกอบหน้า HTML สารบัญ agenda ชุดสี (script ไม่ใช้ token)
validate_book.py              ตรวจเชิงกลทั้งเส้น ถ้าไม่ผ่านส่งซ่อมตามรหัสปัญหา 1 รอบ
   ↓
book-kit:book-auditor         1 ตัวต่อบท + 1 ตัวตรวจข้ามบท (รายงานอย่างเดียว)
sync_state.py --merge-audit   รวมเป็นรายงานเดียว บทที่ไม่ได้ตรวจกลายเป็นประเด็นระดับ critical
                              ประเด็นที่ยังเปิดจากรายงานก่อนหน้าถูกยกมาด้วย
   ↓
รายงาน → ถามคุณ → หยุด       (แก้ได้เมื่อคุณพิมพ์ /book-kit:apply-fixes เท่านั้น: hook บันทึก script ตรวจ 1 คำสั่ง = 1 รอบ)
```

`book-kit:book-builder` ดูแลหน้าตา (ชุดสี, template) ผ่าน `/book-kit:design`

| `audit.max_source_spot_checks` | `10` | จำนวนจุดในต้นฉบับที่ audit หนึ่งรอบเปิดตรวจได้ แบ่งให้ auditor รายบทโดยไม่เกินจำนวนนี้ (ยกเว้นทุกบทได้อย่างน้อย 1) |
| `audit.max_fix_batches` | `5` | จำนวนรอบแก้สูงสุดต่อรายงาน audit หนึ่งฉบับ ครบแล้ว script ไม่อนุมัติรอบใหม่ ให้สั่ง `/book-kit:audit-book` เพื่อออกรายงานฉบับใหม่ (ประเด็นที่ยังเปิดถูกยกไปด้วย) |
| `audit.approval_gate` | `"auto"` | `auto` = script ตรวจว่ามีการพิมพ์ `/book-kit:apply-fixes` ก่อนเริ่มแก้ทุกรอบ (มีผลเมื่อ hook ของ plugin เคยทำงานในโปรเจกต์นี้) `off` = ไม่ตรวจด้วย script ใช้เมื่อเครื่องรัน hook ไม่ได้ |

## การตอบโจทย์ requirement v2-2

1. **หัวข้อย่อยหลายระดับ:** id แบบจุดลึกได้ไม่จำกัด anchor `#sec-2-2-1` สารบัญและ agenda ซ้อนตามระดับ validator ตรวจว่า parent ครบ ระดับ heading และเลขที่แสดงตรงกับ id และเรียงตาม plan
2. **ตั้ง config แบ่งระดับการสรุป:** `content.level` 1 หรือ 2 ทั้งสองระดับใช้ plan ชุดเดียวกันจึงครอบคลุมเท่ากัน draft เก็บแยกตามระดับ script ไม่ยอม build ถ้า draft ไม่ตรงระดับ หัวข้อที่มีแต่ชื่อไม่ผ่าน validator ในทุกระดับ และมีหลักฐานเชิงกล 3 อย่างว่าเนื้อหาสำคัญไม่หายในระดับ 1
3. **เข้าใจง่าย กระชับ ชัดเจน เห็นภาพ:** กติกาเนื้อหาข้อ 4–5 และกติกาของ writer auditor มีข้อตรวจ "เห็นภาพ" แยกต่างหาก validator เตือนเมื่อศัพท์เดียวกันถูกแปลสองแบบ
4. **เสริมเนื้อหาและรูปเฉพาะที่จำเป็น:** architect ขอเนื้อหาเสริมใน plan พร้อมเหตุผล writer ติด `data-supplement` หน้าแสดงป้าย "เนื้อหาเสริม" validator เทียบ id ระหว่างหน้ากับ plan และเตือนถ้าอยู่ผิดหัวข้อ
5. **แก้ไขหรือเพิ่มบทภายหลัง:** ตรวจจับไฟล์ที่เพิ่ม เปลี่ยน ลบ ย้าย และเปลี่ยนเลขบท ต้นฉบับที่เปลี่ยนแต่ยังไม่อ่านใหม่ และ draft ที่เก่ากว่า input ถูกจับด้วย script ระบบเขียนใหม่เฉพาะหัวข้อที่กระทบ เมื่อไฟล์ถูกอ่านใหม่ เลข unit ใน plan เลื่อนตามด้วย script unit ใหม่ที่ยังไม่มีที่อยู่ block จนกว่า plan จะตอบ และ unit ที่ถูกแก้ตรงตำแหน่งเดิมค้างในบันทึกจนกว่า architect จะยืนยัน หัวข้อที่ถูกลบออกจาก plan อยู่ในหน้าต่อไม่ได้
6. **UI สวย มีสีสัน ถูกหลัก:** ดูหัวข้อ "หน้าตาและชุดสี" ขั้นต่ำครบ: สารบัญและ agenda, progress รายหน้าและทั้งเล่ม, ธีมสว่างและมืด, รองรับมือถือและการพิมพ์, โฟกัสคีย์บอร์ดมองเห็นได้ สีที่ writer เขียนตายตัวลงใน draft (ซึ่งไม่เปลี่ยนตามธีม) ถูก script จับ
7. **กัน infinite loop จาก audit:** REPORT → ASK → STOP เป็นกติกาข้อแรก และมีการบังคับเชิงกล 3 ชั้น: คำสั่งแก้ Claude เรียกเองไม่ได้ script อนุมัติรอบแก้ได้เมื่อมีบันทึกว่าคุณพิมพ์ `/book-kit:apply-fixes` (1 คำสั่ง = 1 รอบ บันทึกที่พิมพ์ก่อนรายงานถามถือเป็นโมฆะ) และรายงานหนึ่งฉบับมีเพดานจำนวนรอบ auditor ไม่มี shell และ Claude Code ปฏิเสธการแก้ไฟล์ใน `book/` กับ `sources/` draft ที่ถูกแก้ระหว่าง audit กลายเป็นประเด็น critical และประเด็นที่ยังไม่ได้แก้ไม่หายไปเมื่อมี audit รอบใหม่
8. **ครบถ้วน ถูกต้อง แม่นยำ:** unit นับจากเนื้อ extraction ทุก unit ต้องอยู่ใน plan ที่ใดที่หนึ่งพอดี extraction ต้องอ่านถึงหน้า สไลด์ หรือบรรทัดสุดท้าย (ถ้านับไม่ได้ ระบบรายงานว่ายังไม่ได้ตรวจ) หัวข้อที่ครอบคลุม unit ต้องมีเนื้อหาจริง รูปที่อ่านไม่ได้ถูกแจ้ง auditor สุ่มเทียบ extraction กับต้นฉบับ และเทียบ draft กับ extraction ราย unit
9. **ใช้ token เหมาะสม:** อ่านต้นฉบับครั้งเดียวต่อเวอร์ชันและทำต่อจากที่ค้างได้ build ไม่ใช้ token สลับระดับกลับไม่เสีย token writer และ auditor อ่านเฉพาะ slice ของบทตัวเอง auditor อ่าน draft ไม่อ่านหน้า build orchestrator ตัดสินจากผลของ script ไม่เปิดไฟล์ state เอง

## คำถามที่พบบ่อย

**แก้ PDF บทเดิมไปหนึ่งไฟล์ ต้องทำอะไร:** วางไฟล์ทับแล้วสั่ง `/book-kit:update-book` ระบบอ่านใหม่เฉพาะไฟล์นั้นและเขียนใหม่เฉพาะหัวข้อที่ unit ของมันเปลี่ยน

**อาจารย์แทรกบทใหม่ตรงกลาง:** เปลี่ยนเลขโฟลเดอร์และเลขไฟล์ของบทที่อยู่ถัดไปให้ครบทั้งบท วางบทใหม่ แล้วสั่ง `/book-kit:update-book` เลขบท หัวข้อ ลิงก์ และสถานะการอ่านของผู้อ่านเลื่อนตามโดยไม่เขียนบทเดิมใหม่

**build ค้างกลางทาง:** สั่งคำสั่งเดิมซ้ำ extraction และบทที่เสร็จแล้วไม่ถูกทำซ้ำ

**เปลี่ยนชื่อหนังสือหรือชุดสี ต้องเสีย token ไหม:** แทบไม่เสีย `/book-kit:update-book` จะรัน script build อย่างเดียวเมื่อไม่มีเนื้อหาต้องเขียน

**audit เจอปัญหาแต่ยังไม่อยากแก้:** ตอบปฏิเสธได้ รายงานจะถูกตั้งเป็น `declined` และหนังสือไม่ถูกแตะ ถ้าไม่ตอบแล้วไปสั่ง `/book-kit:update-book` ประเด็นที่ยังเปิดอยู่จะถูกยกไปอยู่ในรายงานฉบับถัดไป ไม่หายไปไหน

**ตอบ "ใช่ แก้เลย" แล้ว Claude ไม่แก้:** ตั้งใจ ตั้งแต่ v11.4 การอนุมัติคือการพิมพ์ `/book-kit:apply-fixes` เพราะเป็นสิ่งเดียวที่ script แยกได้แน่นอนว่ามาจากคุณ ไม่ใช่จาก Claude เอง

**`--set-audit approved` ตอบ `audit.gate` ทั้งที่พิมพ์คำสั่งแล้ว:** แปลว่า hook ไม่ได้บันทึกคำสั่งนั้น (เช่น hook ถูกปิดหลังจากเคยทำงาน หรือเครื่องไม่มี `python3`/`python` ใน PATH ของ shell ที่ Claude Code ใช้รัน hook) แก้ที่ต้นเหตุ หรือตั้ง `"audit": {"approval_gate": "off"}` ใน `book.config.json`

**แก้ครบ 5 รอบแล้วยังมีประเด็นค้าง:** script จะไม่อนุมัติรอบที่ 6 (`audit.batches`) ประเด็นที่แก้หลายรอบไม่หายมักต้องการการตัดสินใจของคุณ อ่านรายงาน แล้วสั่ง `/book-kit:audit-book` เพื่อออกรายงานฉบับใหม่ หรือเพิ่ม `audit.max_fix_batches`

**scan แจ้งว่าไฟล์ PowerPoint มีรูปที่อ่านไม่ได้:** ถ้ารูปเป็นแค่ของตกแต่ง ไม่ต้องทำอะไร ถ้ารูปคือเนื้อหา (แผนภาพ สมการที่เป็นรูป ภาพหน้าจอ) ให้ export ไฟล์นั้นเป็น PDF วางใน `sources/` แทน แล้วสั่ง `/book-kit:update-book`

**สั่ง `--rewrite` แล้วรันค้าง ต้องใส่ `--rewrite` อีกไหม:** ไม่ต้อง คำขอถูกบันทึกไว้กับแต่ละบท สั่ง `/book-kit:build-book` หรือ `/book-kit:update-book` เฉย ๆ ระบบจะเขียนบทที่ยังไม่ถูกเขียนใหม่ให้ครบ

**validate เตือน `draft.hard_colour` แต่รูปนั้นตั้งใจใช้สีจริง (เช่น บทเรียนเรื่องสี):** เป็นคำเตือน ไม่บล็อก auditor ถูกสั่งให้ปล่อยรูปที่เนื้อหาคือสีนั้นเอง

**มีสูตรคณิตศาสตร์เยอะ:** ตั้ง `"math_katex_cdn": true` แล้วสั่ง `/book-kit:build-book --rewrite` (บทที่เขียนไปแล้วต้องเขียนใหม่จึงจะใช้ไวยากรณ์ LaTeX)

**อยากให้ writer ใช้โมเดลที่แรงกว่า:** ตั้ง `"pipeline": {"models": {"writer": "opus"}}`

**ความคืบหน้าการอ่านเก็บที่ไหน:** localStorage ของ browser ผู้อ่าน หัวข้อนับว่าอ่านแล้วเมื่อเลื่อนผ่านท้ายหัวข้อ ไม่นับตอนเพิ่งเปิดหน้า

**พิมพ์ "สร้างหนังสือให้หน่อย" แล้ว Claude ไม่ทำ:** ตั้งใจ คำสั่งที่กิน token ต้องพิมพ์เอง Claude จะบอกคำสั่งให้

## ข้อจำกัดที่ทราบ

- **ยังไม่เคยรันทั้ง pipeline ใน Claude Code จริง** script และหน้าหนังสือผ่านชุดทดสอบ แต่ prompt ของ agent และคำสั่งยังไม่ถูกพิสูจน์ด้วยการรัน การ build ครั้งแรกคือการทดสอบจริง
- **ด่านอนุมัติเป็นตัวกัน loop ที่เกิดโดยไม่ตั้งใจ ไม่ใช่ระบบรักษาความปลอดภัย** session มีสิทธิ์เขียนใต้ `.book-state/` และรัน script ได้ โมเดลที่จงใจแก้ `gate.json` หรือเรียก `gate_hook.py` เองจึงไม่ถูกหยุดด้วยด่านนี้ สิ่งที่ทดสอบแล้วบน Claude Code 2.1.290 (`claude -p` โดยไม่ล็อกอิน): hook ทำงานเมื่อพิมพ์คำสั่ง `command_name` ที่ได้คือ `book-kit:apply-fixes` แบบย่อ `/apply-fixes` ก็นับ และการพิมพ์ชื่อคำสั่งปนในประโยคไม่นับ สิ่งที่ยังอิงเอกสารอย่างเดียว: การที่โมเดลเรียก skill เองไม่ทำให้ event นี้เกิด
- การจับคู่ "unit ถูกแทนที่ตรงตำแหน่งเดิม" ใช้ตำแหน่งเป็นหลักฐาน: ระหว่าง unit ที่ไม่เปลี่ยนสองตัว ถ้า unit เก่าหายไปเท่ากับจำนวน unit ใหม่ที่เพิ่มมา ถือว่าแทนที่กันตามลำดับ ถ้าเนื้อหาใหม่เป็นคนละเรื่องจริง ๆ architect ต้องย้ายเอง รายการนี้ค้างในบันทึกและถูกแจ้งซ้ำจนกว่า architect จะยืนยัน แต่ไม่บล็อก ถ้า architect ไม่ตอบ คำเตือน `plan.replaced_unreviewed` จะไปถึง auditor ซึ่งเป็นด่านสุดท้าย
- การตรวจสีตายตัวดูเฉพาะ attribute ของ tag (`fill`, `stroke`, `color`, `style` ฯลฯ) ที่เป็นค่า hex, `rgb()`/`hsl()` หรือชื่อสี สีที่ซ่อนอยู่ในรูปแบบอื่น (เช่น `color-mix()` ที่ผสมชื่อสี) ไม่ถูกจับ และเป็นคำเตือน ไม่บล็อก เพราะรูปบางรูปมีเนื้อหาเป็นสีนั้นเอง
- การกันแก้ `sources/` และ `book/` บังคับที่เครื่องมือแก้ไฟล์ และ agent 4 ใน 5 ตัวไม่มี shell แต่ orchestrator และ builder ยังรันคำสั่งได้ ควรสำรองต้นฉบับไว้นอกโปรเจกต์
- รูปภาพใน `.pptx`/`.docx` และสมการแบบ object ฝัง (Equation Editor 3.0, MathType) อ่านไม่ได้ ระบบนับ แจ้งชื่อไฟล์ และเตือน auditor แต่ไม่รู้ว่ารูปนั้นสำคัญหรือไม่ การตัดสินใจ export เป็น PDF เป็นของคุณ
- PDF ที่เข้ารหัสหรือโครงสร้างผิดปกติ ระบบนับหน้าเองไม่ได้ จะมีคำเตือน `extraction.length_unverified` ติดตั้ง `pypdf` แล้วมักนับได้
- การตรวจ "อ่านถึงท้ายไฟล์" และ "หัวข้อไม่ว่าง" ตรวจได้ว่า **มี** ไม่ได้ตรวจว่า **ถูกหรือครบทุกประโยค** ส่วนนั้นยังเป็นหน้าที่ของ auditor ซึ่งเป็น LLM
- แถวตารางที่ยาวเกิน 1,800 ตัวอักษรในไฟล์ Office ไม่ถูกตัดบรรทัด (ตัดแล้วจะไม่เป็นตาราง)
- การพิสูจน์ว่า unit ไม่ถูกแตะหลังแก้ต้นฉบับ อาศัยเลขบรรทัดหรือเลขสไลด์ที่ analyst ใส่ไว้ ถ้า unit สรุปเนื้อหาจากนอกช่วงที่ตัวเองอ้าง การแก้นอกช่วงนั้นจะไม่ทำให้ unit ถูกอ่านใหม่ (ช่วงที่เปลี่ยนยังถูกอ่านและได้ unit ของตัวเอง) ส่วน PDF ที่ถูกแก้ต้องอ่านใหม่ทั้งไฟล์ และจำนวนหัวข้อที่ถูกเขียนใหม่ขึ้นกับว่า analyst คงถ้อยคำของ unit ที่ไม่เปลี่ยนไว้ได้แค่ไหน
- การเปลี่ยน `content.audience` / `content.style_notes` ไม่เขียนบทเดิมใหม่ ต้องสั่ง `/book-kit:build-book --rewrite` เองถ้าต้องการให้ทั้งเล่มใช้สำนวนใหม่
- คำถามทบทวนที่ถูกปิดถูกซ่อนด้วย CSS ไม่ได้ถูกลบออกจาก draft
- auditor ยังมีสิทธิ์เขียนไฟล์ใน `.book-state/` เพราะต้องเขียนรายงานของตัวเอง การแก้ draft ระหว่าง audit จึงถูก **ตรวจจับ** ไม่ได้ถูก **กัน**
- หลักฐานเชิงกลของระดับ 1 (คำสำคัญ บรรทัดความหมายสัญลักษณ์ ขั้นตอน) ตรวจได้ว่า "มีอยู่" ไม่ได้ตรวจว่า "ถูก" ความถูกต้องยังเป็นหน้าที่ของ auditor
- เลขบทและหัวข้อต้องเป็นตัวเลขแบบจุด เลขบทเป็นจำนวนเต็ม
- ฟอนต์ที่ฝังเพิ่มขนาดหนังสือแต่ละเล่มราว 150 KB
